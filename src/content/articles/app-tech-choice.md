> 本文的选择顺序是面向新手的建议，不是框架性能排名。平台能力和收费条件以对应官方文档为准；同一框架的不同版本、扩展与目标平台，需按实际项目核对。

## <span class="role-tag me">🧑 你来做</span> 不会编程，先选技术还是先说想法？

**先说产品要做什么，再选技术。** 你不用先回答“喜欢哪种编程语言”，而要告诉 Claude / Codex：给谁用、在哪种手机上用、最重要的操作是什么。

比如，假设你要做物品记录 App：输入物品名称和位置，保存后能搜索。如果首发只服务 iPhone 用户，就先评估 iOS 原生路线；如果首发用户同时用 iPhone 和安卓，就把跨平台方案纳入比较。这里是选择示例，不是已完成的产品案例。

再把可能影响方案的功能单独写出来：是否要拍照、录音、连接外部设备，或者在离开页面后继续执行任务。不要只写“和某个 App 一样”。让 AI 先核对这些功能，再做首页。

已有项目时，把目录交给 AI 检查。建议先问“现在的方案能否满足需求”，不要直接要求换成热门框架。本页解决的是项目选型，不是编程课程清单。

## 原生、Flutter、React Native、uni-app，分别在什么情况下考虑？

原生开发在这里指直接按目标手机平台的开发体系做 App。跨平台框架则帮助项目在不同平台复用代码。插件或扩展，是接入框架之外功能的现成组件；能否用于你的项目，需要核对支持范围。

下面按同样的条件比较。**“优先评估”是建议起点，不是适用性的保证。**

| 路线 | 建议优先评估的情况 | 需要接受的取舍 | 让 AI 先交付什么证据 |
| --- | --- | --- | --- |
| 原生 | 首发只做某个平台，产品重点依赖该平台能力 | 不预设这份实现以后可以直接用于另一个手机平台 | 关键功能的官方依据和目标手机测试结果 |
| Flutter | 明确要做 iOS 和安卓，希望共用项目；或已有合适的 Flutter 底子 | 平台专属功能仍可能要接插件或补适配 | 核心功能的插件支持情况、各端运行和打包办法 |
| React Native | 明确要跨平台，已有适用的 React Native 项目；或希望评估现有 React 项目的可复用部分 | React 网页界面不能直接当成手机界面交付，仍有原生组件与平台差异 | 哪些内容能复用、哪些要重做，以及关键功能的手机演示 |
| uni-app | 除 App 外还确实需要小程序，或已有合适的 uni-app 项目 | 要逐项核对目标端支持情况，并区分开发工具与打包服务费用 | 必需功能在 App 和小程序各端的支持清单与实际测试 |

这些能力各有官方依据：[Apple 的 SwiftUI](https://developer.apple.com/swiftui/) 面向苹果平台；[Flutter 平台集成文档](https://docs.flutter.dev/platform-integration) 说明可共用代码构建多平台应用，也说明部分能力需要插件或平台专属实现。

[React Native 入门文档](https://reactnative.dev/docs/tutorial/) 明确它使用原生组件，而不是网页组件；[DCloud 的 uni-app 介绍](https://uniapp.dcloud.net.cn/) 列出了 iOS、Android、Web 和小程序等目标平台。这些事实支持把它们放入候选，但不能直接证明你的功能已经可用。

## Flutter 和 React Native 怎么选，能不能直接给个答案？

**有合适的现成底子，先验证底子；从零开始，先验证最关键的手机功能。** 对不会编程的人，建议把判断重点放在能否完成产品和持续修改上。

让 AI 对同一份需求回答：相关功能有没有可用扩展？是否支持目标平台？现有电脑怎样开发和打包？出问题时需要补哪些平台专属代码？答案必须落到你的功能，不能只是“生态好”“性能强”。

Flutter 官方说明，现有插件不满足时可以编写平台专属代码；[React Native 的原生平台文档](https://reactnative.dev/docs/native-platform) 也说明可以连接原生代码来补充平台功能。因此，不能因为选择了跨平台，就把这部分工作从计划里删掉。

如果已有 React 网站，可以把 React Native 放入候选，但先让 AI 列清能复用什么。React Native 官方说它使用原生组件，这和直接搬过去网页界面不同。没有已有代码、关键功能也没有明显差异时，就让 AI 选出理由明确的主方案，先完成手机验证，不必反复改选。

## uniapp和原生开发区别是什么，uni-app 做 App 可以吗？

可以。uni-app 官方说明，它使用 Vue.js 开发，可面向 App、Web 和小程序等平台。Vue.js 是一种构建界面的技术，你可以让 AI 负责实现，不必先去学习它的语法。

对你的选择来说，区别主要在工作安排：按原生路线做，就围绕目标平台实现和验收；用 uni-app，就先考虑哪些功能共用、哪些目标端要单独处理。**不要把“支持某个平台”理解为“项目里所有功能都已经兼容”。**

如果你既要独立 App，又确定要微信小程序，可以让 AI 优先评估 uni-app。如果实际只做 iPhone App，就不必为了将来可能用到的小程序，提前接受跨端适配工作。不要拿“以后也许需要”代替明确的首发需求。

## uniapp收费吗，为什么免费工具还会出现账单？

[DCloud 的选型说明](https://uniapp.dcloud.net.cn/select.html) 写明，uni-app 和 HBuilderX 开发工具免费。但开发工具与云打包不是同一项服务。云打包指把生成安装包的工作交给云端完成。

[DCloud 云打包文档](https://uniapp.dcloud.net.cn/dev/app/cloud-build.html) 列有免费打包额度，也列出了次数不足时购买次数、体积超限等计费情形。**不能据此把整个 App 项目预算写成免费。** 具体以官网当前价格为准，本文不提供统一总价。

让 AI 在选型时列出项目实际会用的服务，并附官方计费入口。看到付款提示，先确认收费对象和触发条件，再决定继续还是调整方案。

## 一套代码同时出 iOS 和安卓，哪些工作还要分别做？

共用代码是可行方向，但建议把开发环境、平台功能和手机验收分别列清。React Native 的[平台专属代码说明](https://reactnative.dev/docs/platform-specific-code) 明确，某些组件属性只适用于特定平台，也允许分别实现 iOS 和安卓部分。

先让 AI 做出真实核心流程，再在各个目标平台检查。例如物品记录 App，要实际新增、搜索、修改、关闭重开；如果加入拍照，就同时检查允许和拒绝相机权限后的表现。测试内容按你的功能增减，不要只比较首页是否长得一样。

另外，跨平台选型不会自动解决开发设备问题。Flutter 的官方环境说明将本机 iOS 开发设置列为 macOS 路线。只有 Windows、又要做 iPhone App 时，接着看 [没有 Mac 能开发 iOS App 吗：Windows 做开发，云端打包和上架怎么走](/articles/ios-without-mac/)，让 AI 核对所选项目的打包路径，再决定设备投入。

选型完成的交付物应当是：明确的推荐理由、可运行项目、手机上的核心操作结果，以及还没验证的事项。拿到这些，再继续扩展完整产品。
